# 任务进度调整引擎设计（C2）

> 2026-10-25 起草，同日用户确认（第 13 节）；C3 已实现并验收，C4 加入进度目标文件和离线试算（第 14 节）。

**功能定位**：玩家在官服已有进度时，私服账号可以通过后台把剧情推进到相同位置（补齐前置任务、执行项、世界状态，奖励走邮件），然后从那里无缝接着玩、接着测。它不是给任务打强制完成标记，也不是全解锁工具；目标以外的任务保持未完成或进行中，和官服一致。按「尽量少的一次性工作，更多普适性工作」，引擎对任何账号通用，测试号 2 只是第一个验证对象。
> 依据：`docs/规划.md` 第 1 节「还原游戏」和第 5.1 节；C1 神像对比报告（第 9 节）；牵连分析脚本 `tools/quest-analysis/`（第 3 节）。

## 0. 结论先行

- 后台调整任务**不再打标记**，而是**按任务树重放**：从玩家当前进度开始，按依赖顺序逐个子任务执行「接取 → 补齐完成条件的世界效果 → finish（含 finishExec）」，一直推进到指定子任务为止。
- 现有 `ForcedQuests`（`game/quest/ForcedQuests.java`）只往客户端发 `FinishedParentQuestUpdateNotify`，并在 `player.forcedFinishedQuests` 里记一笔，**服务端存档里没有任何任务、传送点或变量**。测试号 2 的 4372 个「完成」就是这种。重放引擎会逐步替代它：某个主任务真正重放完成后，就把它从 `forcedFinishedQuests` 里移除。
- 奖励一律走邮件，邮件写明来自哪个任务。
- 每次调整前自动备份，并写一份变更日志（journal）。回退以这份日志为准，能退的退，不能退的明确列出。

## 1. 现有代码里和重放相关的事实

| 事实 | 位置 | 对设计的影响 |
|---|---|---|
| `GameQuest.finish()` 依次做：改状态、发包、`finishParent` 时完成主任务、**异步**跑 finishExec、排队 `QUEST_STATE_EQUAL` / `FINISH_PLOT` 事件、`tryUnlockOpenStates()`、发 gainItems **进背包** | `GameQuest.java:226` | 可以直接复用 finish()，但 gainItems 要改道去邮件 |
| `GameMainQuest.finish()` 把 `rewardIdList` 展开后**直接进背包**，再按 `suggestTrackMainQuestList` 接后续主任务 | `GameMainQuest.java:164` | 主任务奖励同样要改道 |
| exec 和事件都提交到 `QuestManager.eventExecutor`：**单线程**，队列上限 1000 | `QuestManager.java:36` | 重放时每一步都要等队列清空（屏障）；引擎不能跑在这个线程里，否则会死锁 |
| 找不到 handler 的 exec 只打一行 debug 日志，然后静默跳过 | `QuestSystem.triggerExec`，`QuestSystem.java:103` | 引擎要在执行前自己查 handler 表，不能靠日志发现 |
| 传送点解锁 `unlockTransPoint` 会顺带：解锁神像所在区域层级、排队 `QUEST_CONTENT_UNLOCK_TRANS_POINT`、刷新神像女神 NPC、生成待领取的传送点奖励 | `PlayerProgressManager.java:941` | 完成条件是「解锁传送点」的子任务，重放时要调用这个方法，而不是只把子任务改成完成 |
| 任务完成条件常常是玩家动作（碰传送点、对话、进区域），它本身**没有对应的 exec** | 例：500006 的 `QUEST_CONTENT_UNLOCK_TRANS_POINT [3,1166]` | 需要一张「完成条件 → 补偿的世界效果」表（第 4.3 节） |
| 已有一批按剧情写的专用补丁类（`Liyue*Recovery`、`MondstadtStoryQuestSupport` 等），在登录时 `resumeOnLogin` | `game/quest/` | 重放完成后要让玩家重新登录，让这些补丁按正常路径走一遍，引擎不直接调用它们 |

神像链的两个关键子任务（从 `quests.json` 查到）：
- **蒙德风神像 3/7**：主任务 352 的子任务 35205，finishCond `FINISH_PLOT 35205`，finishExec 为 `UNLOCK_POINT [3,7]`、`UNLOCK_AREA [3,1]`、`CHANGE_AVATAR_ELEMET [7]`（旅行者获得风元素）。
- **纳塔神像 3/1166**：主任务 5000「纳塔！新的旅程」的子任务 500006「点亮七天神像」，finishCond `UNLOCK_TRANS_POINT [3,1166]`，finishExec 只有 `SET_QUEST_GLOBAL_VAR 7509701=1`。传送点本身由**子任务 30341** 的 `UNLOCK_POINT [3,1166]` 和 `UNLOCK_AREA [3,43]` 解锁（C1 查明）；按依赖顺序重放时，30341 在前，500006 的完成条件已经满足，补偿表只是兜底。

## 2. 总体结构

```
后台网页 ──JSON──> /console/api/quest/*  (WebConsoleHandler 扩展)
                       │
                       ▼
              QuestAdjustService          ← 鉴权、互斥（同一玩家同一时刻只跑一个任务）、备份、journal
                       │
          ┌────────────┼──────────────────┐
          ▼            ▼                  ▼
     QuestPlanner  QuestReplayer     RewardMailSink
     （纯数据，     （逐步执行，        （截获奖励，
      生成计划）     屏障同步）          汇总成邮件）
```

新代码放在 `emu.grasscutter.game.quest.adjust` 包，接口放在 `server/http/console/`。不修改已有专用补丁类。

### 2.1 运行前提

- **玩家必须在线，且在大世界（scene 3）**：现有 exec handler 大量依赖 `player.getScene()` 和会话，离线重放要改的地方太多。不在大世界时接口直接拒绝。
- 重放期间暂停该玩家的输入处理不现实，所以**要求玩家站着不动**；网页上给出提示。重放结束后**强制下线**（kick 并提示重新登录），让客户端重新拉取全部任务、传送点、open state、场景组，也让 `resumeOnLogin` 类补丁正常执行。
- 同一时刻每个玩家只能有一个调整任务，用 uid 加锁。

## 3. 计划阶段（QuestPlanner，只读）

输入：`uid`，目标 `targetSubId`（或目标主任务 + 「完成整个主任务」），模式 `advance`（推进）或 `rollback`（回退）。

1. 从 `GameData` 构建任务依赖图，规则和 `tools/quest-analysis/quest_deps.py` 一致：
   - 主任务内：按 `order` 排序；`acceptCond` 里引用的子任务状态是硬边。
   - 跨主任务：`QUEST_COND_STATE_EQUAL` / `QUEST_CONTENT_QUEST_STATE_EQUAL` / `COMPLETE_ANY_QUEST` 等引用的任务 ID；主任务完成后 `suggestTrackMainQuestList` 的接取。
   - 全局变量：如果某个 acceptCond 读全局变量 X，就从写 X 的 exec 连一条边过来。
2. 从目标子任务**反向求闭包**：要让它完成，哪些子任务必须先完成。只走 `acceptCond` 的硬依赖，加上 `finishParent` 链，**不**顺带推进无关的支线。
3. 闭包内拓扑排序，同层按 (主任务 ID, order) 排序，保证结果确定。
4. 过滤掉玩家存档里已经 `FINISHED` 的子任务。
5. 对每一步预检（第 6 节）：exec 和 cond 是否有 handler、是否属于阻断类型、会写哪些世界状态、会发哪些物品。
6. 输出**计划单**（JSON，也在网页上展示）：步骤列表、预计写入的全局变量 / open state / 传送点 / 区域 / 场景组、预计邮件内容、跳过项、阻断项。**用户在网页上确认后才执行。**

`--dry-run` 等价于只做计划阶段，C3 必须提供。

## 4. 执行阶段（QuestReplayer）

### 4.1 每一步的顺序

对计划里的每个子任务 S：

1. **接取**：S 不在存档里，就 `addQuest`；处于 UNSTARTED 就 `start()`（会执行 beginExec）。不再检查 acceptCond，因为依赖已经由计划保证；但要把实际的 acceptCond 求值结果写进 journal，供排查。
2. **屏障**：往 `eventExecutor` 提交一个空任务并等待（超时 10 秒）。
3. **补齐完成条件的世界效果**：按第 4.3 节的表处理 S 的 finishCond。
4. **屏障**。
5. **完成**：调用 `S.finish()`。finishExec、事件、`tryUnlockOpenStates`、`finishParent` 都走原有路径；奖励被 RewardMailSink 截获（第 5 节）。
6. **屏障**，然后核对：S 是 FINISHED；本步计划写入的状态都已落地（变量值、传送点、open state）。不一致就记为 `MISMATCH`，按策略停止或继续（默认停止）。
7. 写 journal，记下这一步实际改动的前后值。

每 50 步保存一次玩家，避免中途崩溃丢失太多 journal 和存档的一致性。

### 4.2 不在计划里的「顺带反应」

finish() 发出的事件可能让**计划外**的任务被接取，甚至被完成（例如别的子任务的完成条件是「某任务完成」）。处理办法：

- 接取：允许，这正是「后续任务的接取」。journal 记为 `side_accept`。
- 完成（C4更新）：禁止计划外任务顺带完成。事件条件进度在写入前就由重放上下文拦截；只有重放器当前明确调用的子任务可以finish。接取仍走正常路径，计划外任务保持进行中，留给用户接着玩。
- 防漏检查：如果运行适配器仍报告计划外任务完成，保留journal并停止后续步骤，不把越界当成成功。

### 4.3 完成条件补偿表

完成条件描述的是「玩家做了什么」，强制完成时要把这个动作在世界里留下的痕迹补上。表按 content 类型维护，C3 至少实现下面这些，其余记录后跳过：

| finishCond 类型 | 补偿动作 | 说明 |
|---|---|---|
| `QUEST_CONTENT_UNLOCK_TRANS_POINT [scene, point]` | `progressManager.unlockTransPoint(scene, point, isStatue)` | 神像会顺带解锁区域层级、刷新女神 NPC；首解锁的传送点奖励按第 5 节进邮件 |
| `QUEST_CONTENT_UNLOCK_AREA` / `ENTER_AREA` 类 | `unlockSceneArea(scene, area)` | 只补区域解锁，不传送玩家 |
| `QUEST_CONTENT_COMPLETE_TALK` / `FINISH_PLOT` | 把对话记为已完成（存档里的 talk 记录） | 不播剧情 |
| `QUEST_CONTENT_ENTER_DUNGEON` / `FINISH_DUNGEON` | 无 | 秘境首通奖励不补；报告里列出 |
| `QUEST_CONTENT_OBTAIN_ITEM` | 无 | 物品由前序步骤的 exec 或 gainItems 发放 |
| `QUEST_CONTENT_QUEST_VAR_*` / `GLOBAL_VAR_*` | 把变量设到满足条件的值 | 先看前序 exec 是否已经写过 |
| `QUEST_CONTENT_MONSTER_DIE` / `KILL_*` / 交互 gadget 类 | 无，只完成任务 | 对应场景组按 exec 刷新 |
| 其它 | 无 | journal 记 `cond_unhandled` |

### 4.4 不重放的「表现类」exec

重放的目的是把**存档状态**推到正确位置，不是把剧情演一遍。下面这类 exec 只影响当下画面，或者会把玩家拉走，重放时**跳过并记录**：传送（`TRANS_SCENE*`、`TELEPORT*`）、播 CG / 过场、天气、镜头、临时换队。C4更新：试用角色GRANT_TRIAL_AVATAR / REMOVE_TRIAL_AVATAR及后缀变体一律跳过并记journal，不要求配对；收尾清除已有试用身份并恢复正式队伍。Lua通知不能整体当成表现类，按审计策略执行或阻断，见《任务调整-NOTIFY_GROUP_LUA审计》。

`CHANGE_AVATAR_ELEMET`（旅行者元素）这种会改存档的 exec **不属于**表现类，必须执行。

## 5. 奖励：一律邮件

用户要求：后台解锁任务时，任务原本的奖励**不直接进背包**，全部通过邮件发送，邮件写明来自哪个任务。

**截获点**（RewardMailSink，重放期间对该玩家生效，用 `ThreadLocal` 加 uid 判断，结束时一定在 `finally` 里关掉）：
1. `GameMainQuest.finish()` 里 `rewardIdList` 展开的物品。
2. `GameQuest.finish()` 里的 `gainItems`。
3. 发物品类 exec（具体类型以牵连分析统计为准）。
4. 补偿传送点时首次解锁产生的「待领取传送点奖励」：保持原有的待领取机制，不提前发放，因为原版就是玩家点击后领取的。
5. 其它在重放期间以 `ActionReason.QuestReward` / `QuestItem` 进背包的物品，作为兜底。

在 `Inventory.addItem*` 入口按「当前是否处于该玩家的重放上下文」判断；在上下文内就把 `(itemId, count, 来源主任务, 来源子任务)` 记进账本，不入包。

**邮件格式**（每个主任务一封；附件超过上限时拆成「(1/2)」「(2/2)」）：
- 标题：`任务奖励补发：<主任务中文名>（<主任务 ID>）`，中文名缺失时用 `主任务 <ID>`。
- 正文：本次由管理后台推进；列出这封邮件对应的子任务 ID 和名称；每件物品来自主任务奖励（rewardId）、子任务 gainItems，还是某个 exec。
- 有效期：沿用 `SystemMailHelper.DEFAULT_EXPIRE_SECONDS`。
- 邮件 ID 写进 journal，回退时用。

**例外：任务道具直接进背包**（2026-10-25 用户确认）。任务道具（`MATERIAL_QUEST` 一类，以物品表的 materialType 判断）在剧情中途会被后续条件检查，或被 `DEL_PACK_ITEM` 之类的 exec 扣掉，所以不经过 RewardMailSink，按原有路径直接进背包、按原有 exec 扣除。journal 照样记录它们的增减。其余奖励全部走邮件。

## 6. 服务端没实现的 exec / cond

预检把每个类型分成三类，名单来自牵连分析脚本的 `handled / enum_only / missing` 统计，再人工标注：

| 类别 | 例子 | 处理 |
|---|---|---|
| **可跳过**：表现类，或只影响已下线的玩法 | 过场、天气、`ADD_ABYSS_WAR_ACCOUNT_DATA` 之类 | 跳过，journal 记 `skipped_exec` |
| **阻断**：会写存档状态，并且被后续 cond 读取 | 写变量、写 open state、改场景组的类型，只要没 handler | **计划阶段就拒绝推进到这一步之后**；计划单写明卡在哪个子任务、哪个 exec，以及需要先实现什么 |
| **未知**：还没标注过的类型 | 新版本新增的类型 | 默认按阻断处理；网页上可以勾选「本次按跳过处理」，勾选结果写进 journal |

cond 同理：acceptCond 的 handler 缺失不影响重放（依赖由计划保证）；finishCond 的 handler 缺失只影响第 4.3 节的补偿是否完整，记录即可。

结果汇总在计划单和执行报告里：「执行 N 步，跳过 exec M 个（按类型列），阻断 0 个」。

## 7. 备份和 journal

**改动前自动备份**（Service 在执行阶段的第一步做，备份失败就整体中止）：
- 文档范围：`players` 里该 uid 的文档、该 uid 的所有任务文档（GameMainQuest 集合）、邮件、物品、角色，以及按 ownerUid 关联的场景组、世界数据。C3 实现时按实际集合名补全（C1 已导出过这些集合，可以直接参照）。
- 位置：`astaps-trial/backups/quest-adjust-<uid>-<YYYYMMDD-HHMMSS>/`，每个集合一个 JSON 文件，加一份 `manifest.json`（时间、计划单、服务端提交号）。
- 只追加、不覆盖；保留最近 20 份，更早的由用户自己删。

**journal**：和备份放在一起，`journal.jsonl`，每步一行：子任务 ID、动作、前值和后值（任务状态、变量、open state、传送点、区域、场景组 suite、物品账本、邮件 ID）、跳过项、`side_*` 项。

## 8. 回退

回退的含义：把玩家拉回到「目标子任务尚未完成」的状态。分两种：

**A. 撤销某次调整**（推荐）：按该次 journal 倒序还原。

| 能回退 | 做法 |
|---|---|
| 子任务和主任务状态、进度、任务变量 | 还原 journal 前值；本次新建的任务文档直接删除 |
| 全局变量 | 还原前值 |
| open state | 只还原本次从 0 变成非 0 的那些 |
| 传送点、区域 | 只移除本次新增的；客户端在重新登录后才会刷新地图 |
| 场景组 suite、组变量 | 还原 `QuestGroupSuite` 和组变量前值 |
| `forcedFinishedQuests` | 加回本次移除的 ID |
| **未领取**的补发邮件 | 删除 |

| 不能回退（报告里列出，交给人判断） | 原因 |
|---|---|
| **已领取**的补发邮件里的物品 | 已进背包，可能已经消耗；不从背包里扣，避免扣成负数或误扣玩家自己获得的同类物品 |
| 已领取的传送点、神像奖励 | 同上 |
| 成就、手册、纪行等 watcher 进度 | 由事件触发，散落在多个模块，没有统一的前值 |
| 旅行者元素、已解锁角色 | 可以技术上改回，但会牵连天赋和命座；默认不动，单独列出 |
| 调整之后玩家自己正常推进的进度 | journal 只覆盖本次调整；如果检测到之后有新的任务变化，撤销前先在网页上警告 |

**B. 回退到某个子任务**（不依赖 journal，用于正常推进过的号）：复用现有 `GameMainQuest.rewindTo` 的思路，把同一主任务里 order 大于目标的子任务清掉，再从依赖图正向找出「因为这些子任务完成才被接取的任务」一并清掉。世界状态只回退能确定是这些子任务的 exec 写的部分（来源从依赖图反查），确定不了的只报告、不动。这一种风险高，C3 先做 A，B 放在第二期。

**整库或整档恢复**仍然只用备份目录，且必须由用户明确要求，不作为后台按钮。

## 9. 测试号 2 的修复方案

> C1 完整报告：`astaps-trial/backups/quest-adjust-20261025-012425/C1-神像对比报告.md`（共 696 条差异，可用 `tools/quest-analysis/statue_compare.py` 重跑）。对照号是个人号 100324832，并用 100000001 交叉核对，两号都真实完成了 35205。

**C1 结论（Claude 已对照 TalkExcel 核实）**：蒙德神像不能交互，不是因为传送点没解锁，而是因为**神像入口对话的门槛不满足**。对话 31141（npc 1201）的 beginCond 是 `QUEST_COND_STATE_EQUAL [35205, 3]` 和 `QUEST_COND_SCENE_AREA_UNLOCKED [3, 1]`。测试号 2 的区域早就解锁了，但**存档里根本没有 35205 这个子任务**，强制标记只存在于 `forcedFinishedQuests`。

| 项 | 正常号 | 测试号 2 | 写入来源 |
|---|---|---|---|
| 子任务 35205 状态 | FINISHED | 文档不存在 | `GameQuest.finish()` |
| `forcedFinishedQuests` | 空 | 4372 项 | `ForcedQuests.apply()` |
| `mainCharacterElement` | Wind | 无 | 35205 的 `CHANGE_AVATAR_ELEMET [7]` |
| `unlockedScenePoints[3]` / `unlockedSceneAreas[3]` | 5 / 11 | 1720 / 999 | 正常号来自任务 exec；测试号来自批量写入 |
| `openStates` | 67 | 697 | 测试号来自批量写入 |
| `forceLockedScenePoints[3]` | `[1720]` | 空 | 35106 的 `LOCK_POINT [3,1720]` |

## 14. C4：可核对的进度目标与离线试算（2026-10-25）

用途是**跳过用户在官服已经玩过的剧情，推进到同一进度后接着玩**。不是完成所有任务，也不把 `forcedFinishedQuests` 当成真实进度。任意账号、全新账号均使用同一套目标解析和规划逻辑。

### 14.1 目标格式 v1

```json
{
  "version": 1,
  "source": {
    "description": "官服截图或用户口述",
    "screenshots": ["本机截图路径或说明"],
    "date": "2026-10-25"
  },
  "completeChapters": [{"id": 1001}],
  "archonThrough": {"chapterTitleZh": "为了没有眼泪的明天"},
  "completeParents": [351, {"titleZh": "温迪的新计划"}],
  "completeSubs": [35205]
}
```

这是四种选择器组合的语法示意，所有选择器取**并集**；不需要的字段省略。第一幕示例只使用 `completeChapters:[{"id":1001}]`，见 `data/quest-adjust/goals/example-mondstadt-act1.json`。

- `completeChapters`：数组，指定章节内所有非测试主任务完成。引用可以是数字ID、中文名字符串、`{"id":...}`或`{"chapterTitleZh":"..."}`。
- `archonThrough`：单个章节引用，只在魔神章节范围解析中文名；将资源中该章节及之前的魔神章节全部加入。魔神身份来自 ChapterExcel 的 `CHAPTER_STYLE_TYPE_AQ`，顺序使用资源 `tag`，不能按chapterId大小推断（如1004实际晚于1101）。
- `completeParents`：数组，数字ID、中文名字符串、`{"id":...}`或`{"titleZh":"..."}`。同名时列候选并报错，不猜测。
- `completeSubs`：正整数子任务ID数组，细粒度目标精确停在该子任务，不要求它是finishParent。
- `source`：任意说明对象，保存在解析结果中；截图/口述/日期等只供核对，不能作为跳过策略或越界的授权。

主任务和章节通过只读 `data/admin-catalog/quests.json` 查询名称与归属，并用真实资源校验主任务、子任务和章节存在。缺chapterId但series对应真实章节的序章引导也纳入该章节，所以1001包括351、359、361。主任务标题含`(test)`（忽略大小写）或`$HIDDEN`的条目不由章节选择器选中；正常隐藏步骤仍可作为真实前置，不能按子任务描述里的`$HIDDEN`盲目删掉。

真实资源中“捕风的异乡人”同时命中1001和非魔神章节10174：`completeChapters:["捕风的异乡人"]`会报错列出两者，必须改用1001；`archonThrough`有魔神范围可消歧。显式引用对象只能有一个id或名称字段；未知顶层字段、空目标、缺失资源均报错。主任务若无唯一正常finishParent也报错列出候选，要求使用completeSubs精确指定，不擅自选择结算支线。

章节与主任务展开成finishParent子任务目标；与显式completeSubs合并后交给同一次规划。`QuestPlanner.plan(PlayerState, Collection<Integer>, ...)`执行并集闭包、拓扑排序、去重，原单targetSubId方法仍兼容。计划增加`targetSubIds`、`sideAcceptMainIds`和`progressGoal`，planHash覆盖全部目标及来源；来源随计划进入journal，apply重新校验时使用完整目标集合。

### 14.3 离线入口与锁

`QuestAdjustDryRun`不启动服务端、不实例化Player、不读取数据库；读取真实任务资源、只读admin-catalog名称索引、exec-policy及JSON导出，输出静态计划。handler按当前源码注解扫描，**不能证明运行时注册、Lua执行或世界状态验收**。所有阻断仍保留，工具不会偷偷override。

先按`astaps-trial/BUILD-LOCK.md`创建`astaps-trial/build.lock`，已存在则等待；以下Gradle命令必须放在持锁的`try`块内，并在`finally`仅删除本次创建的锁。全部使用`--no-daemon`。

```powershell
.\gradlew.bat -I tools/quest-analysis/quest-adjust.gradle questAdjustDryRun `
  -Pinput=new `
  -Pgoal=data/quest-adjust/goals/example-mondstadt-act1.json `
  -Pout=build/quest-adjust/act1-new.json `
```

`-Pinput=new`表示无任务文档的空白状态（UID用0作离线占位，不涉及建号）。改成导出目录即可读取该目录的`players.json`、`quests.json`；无任务文档时quests.json写`[]`。支持Mongo extended JSON的整数/长整数包装、枚举或数字任务状态，以及数组或逐行文档格式。必须恰好一个玩家、任务ownerUid一致、父子归属一致；重复文档或未知状态报错。强制完成标记只保留在快照里，不参与任务完成判断。工具只依赖这两份文件进行规划，不能拿它证明背包、角色或运行环境都已校验。输出用CREATE_NEW，已有同名计划不会覆盖。

离线planId没有进入后台计划缓存，不能直接交给apply；将来要执行时必须在线重新生成并核对计划。本次只生成离线计划，不进行该操作。

- 顺带接取预览：模拟步骤开始/完成产生的STATE_EQUAL/NOT_EQUAL接取链，合并建议接取主任务。只模拟接取、不完成；已存在主任务不重复列为新主任务。潜在顺带接取的beginExec也预检，危险项同样阻断。复杂条件、Lua/全局变量的动态接取未完整模拟，因此清单是静态候选，实际以journal为准。
